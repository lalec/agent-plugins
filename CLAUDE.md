# CLAUDE.md

Repository-wide instructions. Plugin-specific rules live under their own headings.

## dev-workflow

Design contract for `plugins/dev-workflow/`. Read before editing anything in it.

### Rules

1. **Agents do WHAT, skills do HOW.** Agents are stack-agnostic step sequences; skills carry the project-specific commands, paths, and tools.
2. **One-way references.** Agents may name skills; skills must never name agents.
3. **Agents and commands are uniform across projects.** Same wording, same structure, only `<PREFIX>` differs — variation belongs in skills.
4. **No duplicated instructions.** A rule lives in exactly one place; if it appears in both an agent and a skill, the boundary is wrong — fix the design, don't copy text.
5. **SKILL.md is *what + when + pointer*; references are *how*.** SKILL.md states what the skill owns, when to invoke it, and routes to references via a short read map. Multi-step protocols, full code examples, and detailed checklists live in `references/*.md`, never inlined in SKILL.md. If a SKILL.md restates a reference's content, the duplication is a bug — collapse it to a pointer.
6. **No hardcoded project-variable content.** Allowed: fixed names (`<PREFIX>-dev/qa/pm`, the 6 lifecycle skill names, the command names). Forbidden: stacks, hosting, paths, ports, or discovery-dependent skill names — route those through `governed-paths.conf` / `deploy-config.yaml` / discovery.
7. **Surgical changes only.** Edit existing structure to fit new concepts; never bolt parallel mechanisms on top.

### Workflow contract (from `plugins/dev-workflow/skills/install/SKILL.md` § Phase 2 `docs/workflow.md` template)

Every install produces this exact shape — preserve it when evolving the plugin.

- **Pipeline:** `/code` or `/fix` → `<PREFIX>-dev` → `<PREFIX>-qa` → `<PREFIX>-pm`.
- **3 agents:** `<PREFIX>-dev` (design → implement → deploy → Reference Sync → handoff; its handoff carries a `Roadmap:` field naming every id it appended at step 1.5, the only way tracked scope reaches the close-out's Emerged block), `<PREFIX>-qa` (review + test → sign-off → handoff; its handoff carries a `Fanned out:` count whenever it split a verification set across parallel children, the only way that spend becomes visible; status vocabulary `signed-off | signed-off-with-deferrals | blocked` — deferrals are the honest word for "clean except unrunnable verifications", so orchestrators never relabel a handoff; may fix **non-source** findings itself, source always routes to dev), `<PREFIX>-pm` (verify QA → write log → docs check → handoff; log hash = the feature commit; runs on `model: sonnet` — its work is mechanical close-out, so Opus is reserved for `<PREFIX>-dev`/`<PREFIX>-qa`).
- **8 lifecycle skills:** `<PREFIX>-log`, `<PREFIX>-review`, `<PREFIX>-debug`, `<PREFIX>-deploy`, `<PREFIX>-test`, `<PREFIX>-skill`, `<PREFIX>-docs`, `<PREFIX>-graph`. `<PREFIX>-design` is added only when a Frontend category is present, and is the single authority for visual values, app-wide interaction patterns, and icon sourcing — it owns `design-tokens.md` (values) and `ux-patterns.md` (the pattern inventory, the consistency sweep every new surface runs first, and the icon rule: the project's declared icon set, else the declared asset skill, **never** hand-authored geometry; a missing generation credential is `blocked`, not a licence to draw one). It names its two external skills by role — design intelligence and asset generation — each replaceable per project; `<PREFIX>-review` cites `ux-patterns.md` so QA re-checks at review what design settled at build time. `<PREFIX>-deploy` is the single source of truth for *how* the project deploys — owns `deploy-config.yaml` and the gate/trigger/verify logic; agents, commands, and other skills delegate here. `<PREFIX>-dev` invokes it for non-prod (mid-pipeline, so QA tests a running stack); **prod deploy is invoked only at the command top level** (`/code|/fix --prod`), never from a subagent, because the gate needs `AskUserQuestion` and that only reaches the user at the top level. The deploy skill is **model-invokable** (no `disable-model-invocation` frontmatter) so the dev step and the command can call it via the Skill tool — "never deploy on whim" is enforced by its description + the prod `user_confirm` `AskUserQuestion` gate, not a frontmatter gate.
- **Commands:** thin entry points that hand work to agents — `/code` and `/fix` start the pipeline at `<PREFIX>-dev`; `/tweak` is the sanctioned iterate lane (top-level, inline-verified, batched close-out enforced by the `close-out-gate` hook at push time); `/revert` is the sanctioned rollback (`git revert`, scoped re-verify, logged reversal); `/tidy` is the WIP-resolution lane (sweep dirty tree/stashes/worktrees/stale branches → history probe before judging any item, since `discard`/`ignore` require evidence that it's superseded rather than accidental → one disposition per item from `commit | deliver | discard | ignore | keep` → apply with self-protecting commands, `discard` as a named stash and `git branch -d` never `-D` → re-sweep as evidence; `/code`, `/fix`, `/pilot` route here when entry WIP overlaps the task's paths, instead of stashing blind); `/pilot` is the autonomous multi-task lane (open with the same `open-deferrals` read `/code` defines — a mission is the main way work starts, so it is one of the three lanes that can discharge a deferral and must therefore raise one; report it as a line and fold only the 3+-on-one-blocker escalation into the gate — then decompose a goal into tasks, gate once up-front — Confirm + Ship in one `AskUserQuestion`, no mid-run questions — route each task to the pipeline or the tweak lane, route each deferral by declared environment shape exactly as `/code` does (non-prod env exists → fix cycle, never accepted; prod-only → carried as `prod-walk:` and walked at close-out after the deploy; out-of-band → deferred with trigger + observable + location) and label what is genuinely deferred `auto-accepted — pilot run`, one batched close-out where prod pre-auth requires a fully clean run: all tasks signed-off, no deferrals, user-answered Ship); `/roadmap` is the entry point from tracked work — it ranks the open items (the project's single rank rule, priority → dependency → category, defined in `roadmap.md § Rank` and cited by `/pilot` rather than restated) and either hands the top set to `/pilot --items <id>,…` or starts one item through `/code`/`/fix`; it selects and never implements, so every run constraint stays in `/pilot`. `/whats-up` is the **composed reader** and the only read-only lane — it opens a fresh session with no handover by reading the six stores that outlive one (git, upstream, roadmap, `custom-tests.yaml`, the log's `parked` gates, the working tree), each with a stated fallback and an unread store reported as a `not done` Status row; a project that runs something unattended adds a **seventh, discovered** store by putting a `whats-up-store:` block (`reads`/`healthy`/`when-bad: degraded|live`) on the command that answers it — the same discovery mechanism as `pilot-lane:`, named by filename, project-owned, skipped with a warning when malformed, so the template stays uniform under Rule 3; a declared store reporting bad outranks gate-blocked. It reconciles before reporting (a `parked` gate is a claim — the log is append-only, so nothing rewrites a past entry — and is only open if no later entry, deploy or tree change answers it), diagnoses **gate-blocked | fragmented | clear** from two numbers, and reports per `code.md § Done` with the ranked `Open` table as the plan and **no** separate action list. It never writes: work at risk becomes the top `Open` row naming the command that saves it. It is the sole sanctioned inversion of the run-scoping rule — its `Emerged` is the standing backlog, **counted per store, never listed** — and the only caller of `open-deferrals --with-fail`, because a recorded `fail` is excluded from that query by design and would otherwise be reachable nowhere once its close-out's `Open` row died with the session. Others target a specific phase (wrap-up, design). `/code` and `/fix` also own the top-level steps the subagents can't do: the Step 0.5 **single gate** (one `AskUserQuestion` call, at most two questions: **Confirm** — whose question text *is* the plan of record, stating the acceptance statement and the 2–3 typed verifications the command derived from it, with the automatic "Other" as the only override channel (restated goal → re-derive + re-ask once; named checks → amend; named scope → pin `regression_mode`; "I'll verify live" → UAT-only, nothing persisted) — and **Ship**, made up-front while the user is present; `--prod`/`--no-push` pre-answer it; Ship's timeout default is always Hold. There is no verification picker and no regression question: the agent owns the set, and scope is `auto` by default, resolved once by `<PREFIX>-test` from the paths dev actually changed, or pinned by `--regression full|smart`), the Step 0 entry report (dirty tree, **unpushed commits** — nothing else raises held work — and open deferrals **split structural/closable**, the structural ones counted rather than listed so the list stays readable), the pre-QA "Ensure verification stack" step (start/restart a serve-env with its `stack:` overrides when a UX/E2E target is down or stale — subagents can't hold servers), the user-gated UAT-defer on a `signed-off-with-deferrals` handoff, the subagent salvage protocol (dead agent → SendMessage/re-spawn, never top-level role absorption), and, with `ship_mode: prod`, the post-sign-off prod deploy via `<PREFIX>-deploy` (whose prod walk drains every still-open prod-only deferral covering the shipped paths, `blast`-bounded — a prod-only check is discharged by *a* deploy, not only by the run that carried it) — pre-authorized by the Ship answer only when the run was clean (clean sign-off, no timeout-auto-decisions, shipped set = reviewed set), else re-gated — plus the final close-out (push per `<PREFIX>-deploy` § Push policy + evidence-verified scorecard). **Close-out report contract:** every command that closes work reports in five blocks — Verdict (one line) · **Learned** (≤3 bullets, often `None` — only what changes what the reader believes or would change a decision; second because it cannot be reconstructed from the diff or the log) · Status · Open · Emerged — then one closing line, and nothing else; with a closed status vocabulary (`needs you` / `failed` / `not done` / `not proven` / `done` / `proven` / `n/a`) where `done` (it happened) and `proven` (something walked it) never substitute for each other. **One test places every row: does it need a decision or an action from you now? Yes → Open, naming the exact command (plus its roadmap id when it has one). No → Emerged, naming the store that holds it (a roadmap `**Id:**`, a `custom-tests.yaml` `last: blocked`, the git tree or a named stash — there is no fourth home, and no home means the row is Open).** Filing is orthogonal to urgency and an item never appears in both blocks: a filed item that still needs you stays in Open, because sorting by "will something raise it again?" sends the most urgent row in the repo to Emerged where it reads as handled. Open's table is **three columns, always** — and the one that may never be dropped is `Next`, which must be a runnable command, never a bare roadmap id. **Open empty means the session is disposable**, and the closing line is *derived* from the Open rows rather than authored: none needing work → `none — safe to start a fresh session`; one → its `Next`; 2+ all carrying roadmap ids → `/pilot --items <id>,…` ranked per `roadmap.md § Rank`; 2+ mixed → the top row's command, never a `/pilot` line that would drop the unfiled silently; a parked gate outranks all of it. Filing is for scope only: a lane with no `<PREFIX>-dev` to append for it (`/wrap`, `/tweak`, `/tidy`, a goal-shaped `/pilot`) appends the roadmap item itself in dev step 1.5's format — `docs/roadmap.md` is `EXEMPT` in PATH_MAP for exactly that reason — while a parked gate or a `fail` is never filed to make Open look empty. This is the close-out half of what Step 0 reads at entry. Stated once in `code.md § Done` and cited by `/fix`, `/wrap`, `/tweak`, `/revert`, `/tidy`, `/pilot`, `/whats-up`; length is cut by folding the rows in a good state, never by dropping an Open or Emerged row. **Gate policy:** every command splits `AskUserQuestion` timeouts by risk — reversible gates proceed with defaults labeled `auto-selected on timeout — not user-confirmed`; irreversible gates (prod deploy, CI-coupled push) park; a timeout is never presented as consent. Same `.md` shape across projects (Claude Code only); concrete set evolves over time.
- **Domain skills:** derived from `CATEGORY_MAP` discovery; path ownership is single-sourced in `<CONFIG_DIR>/hooks/governed-paths.conf`.
- **Hooks:** shell scripts wired in `<CONFIG_DIR>/settings.json` that fire on tool events (`PreToolUse` / `PostToolUse` for Edit, Write, Bash, Skill). Two roles only — *gates* that block actions when an invariant is violated (skill not loaded, dirty tree, uncovered path), and *recorders* that mark session state or warn after the fact. Concrete set evolves; the role split does not.
- **Source-of-truth files:** `governed-paths.conf` (path → skill ownership incl. per-skill self-ownership entries + `DEPLOY_PATHS` + `REF_WATCH`), `deploy-config.yaml` on `DEPLOY_OWNER` (unified env schema — every env declares exactly one of `run:` serve-env / `deploy:` ship-env plus `url`; serve-envs may declare `stack:` for a composed, verifiable local stack; `verify:` is a plain env name; typed verifications resolve to the first non-prod env, never prod), `docs/roadmap.md` (open items; every item carries a permanent `**Id:**` — assign once, never rewrite, since the delivery log cites it), `docs/project-log.md` (delivery log), `custom-tests.yaml` (verifications — agent-authored, never user-assembled: `type` + `paths` select, `last:` records the outcome and carries a `reason` on every `blocked`/`fail`; `last.commit` is the code commit under test, resolved **once** at the start of a run and never re-read per verification, because outcomes are committed as they go — a killed agent then loses one record, not the run's; the end-state check runs in every scope and every retest, `blocked` if unreachable but never dropped). **`full` means every prior is *accounted for*, not re-executed** — one whose `last.status` is `pass` at a commit whose diff to `HEAD` touches none of its `paths:` is carried forward with that range as evidence, reported separately from what was walked, and its `last:` is left untouched; blocked/fail entries, the end-state check, hand-authored flows, and anything with an unresolvable range always execute, and a missing `git` means execute. Carrying is explicitly **not** narrowing a pinned scope; dropping for time or cost is. A set too large for one context is split across parallel children, which is the *cheap* direction (each child accumulates only its share of the output every turn re-reads) — so bound a child's **turns** (~60), never the number of children, and brief each child inline instead of sending it to read the protocol, since that prefix is the one cost that multiplies per child.
- **Delivery graph** (`<PREFIX>-graph`, `.claude/graph/`): a **derived, disposable** typed-edge index projected from the five source-of-truth files plus `git log` — never a source of truth itself, and rebuilt from scratch by `graph.py build`. `graph.py` is copied **verbatim** from the plugin's `shared/graph.py` (glob-discovers skill dirs, so no `<PREFIX>` substitution and byte-identical across projects — fix the plugin, never the copy). `edges.jsonl` is gitignored. Every edge carries a `src` naming the artifact and field it came from, so an answer cites an edge and the edge cites a file. Five queries replace prose re-derivation: `covers` (prior-selection), `blast` (dev's domain identification; `<PREFIX>-test`'s regression-scope resolution on `regression_mode: auto`), `history` (debug/tidy), `roadmap-open` (pm's roadmap linkage; `/roadmap`'s ranking input), `open-deferrals` (`/code`+`/fix` Step 0; `/whats-up`'s unproven-work store, the sole caller of its `--with-fail` flag, which admits a recorded `fail` — excluded by default because the close-out files one in `Open`, where a fresh session cannot reach it). **Every call site must state a fallback** — the graph is an accelerator, never a gate, and must degrade silently when absent, unbuildable, or python3-less. Node ids are exact natural keys (sha7, repo path, verification name, roadmap `**Id:**`), so there is no entity-resolution step and no model call in the projector.
- **Delivery log entry format** (`docs/project-log.md`, written by `<PREFIX>-log`): `### YYYY-MM-DD HH:MM · <7-char hash> — <title>` (hash = feature commit, never bookkeeping) + 1–3 sentences + `**Tests:**` + `**Skills:**` + optional `**Deployed:**` / `**Addresses:**` (roadmap `**Id:**` — the durable roadmap↔delivery link) / `**UAT-deferred:**` (each name followed by a spaced dash and **why it could not run** — the only record of that, and what lets `open-deferrals` sort structural from closable; an entry without one is permanently unclassifiable) / `**Decisions:**` (`<gate>=<value> (<user|timeout|agent|pilot-auto>)` — a timeout, a pipeline-derived value (`agent`, e.g. the resolved regression scope), or an autonomous choice is never recorded as `user`) / `**Checklist:**`. Any field added here must be added in the `<PREFIX>-log` template, the workflow.md template, and the upgrade-pass checklist together. The log is also the delivery graph's primary input — `<PREFIX>-log` reprojects after committing each entry.
