## dev-workflow

Design contract for `plugins/dev-workflow/`. Read before editing anything in it.

### Rules

1. **Agents do WHAT, skills do HOW.** Agents are stack-agnostic step sequences; skills carry the project-specific commands, paths, and tools.
2. **One-way references.** Agents may name skills; skills must never name agents.
3. **Agents and commands are uniform across projects.** Same wording, same structure, only `<PREFIX>` differs — variation belongs in skills.
4. **No duplicated instructions.** A rule lives in exactly one place; if it appears in both an agent and a skill, the boundary is wrong — fix the design, don't copy text.
5. **SKILL.md is *what + when + pointer*; references are *how*.** SKILL.md states what the skill owns, when to invoke it, and routes to references via a short read map. Multi-step protocols, full code examples, and detailed checklists live in `references/*.md`, never inlined in SKILL.md. If a SKILL.md restates a reference's content, the duplication is a bug — collapse it to a pointer.
6. **No hardcoded project-variable content.** Allowed: fixed names (`<PREFIX>-dev/qa/pm`, the 6 lifecycle skill names, the 5 command names). Forbidden: stacks, hosting, paths, ports, or discovery-dependent skill names — route those through `governed-paths.conf` / `deploy-config.yaml` / discovery.
7. **Surgical changes only.** Edit existing structure to fit new concepts; never bolt parallel mechanisms on top.

### Workflow contract (from `plugins/dev-workflow/skills/bootstrap/SKILL.md` § Phase 2 `docs/workflow.md` template)

Every install produces this exact shape — preserve it when evolving the plugin.

- **Pipeline:** `/code` or `/fix` → `<PREFIX>-dev` → `<PREFIX>-qa` → `<PREFIX>-pm`.
- **3 agents:** `<PREFIX>-dev` (design → implement → deploy → Reference Sync → handoff), `<PREFIX>-qa` (review + test → sign-off → handoff; status vocabulary `signed-off | signed-off-with-deferrals | blocked` — deferrals are the honest word for "clean except unrunnable verifications", so orchestrators never relabel a handoff; may fix **non-source** findings itself, source always routes to dev), `<PREFIX>-pm` (verify QA → write log → docs check → handoff; log hash = the feature commit; runs on `model: sonnet` — its work is mechanical close-out, so Opus is reserved for `<PREFIX>-dev`/`<PREFIX>-qa`).
- **7 lifecycle skills:** `<PREFIX>-log`, `<PREFIX>-review`, `<PREFIX>-debug`, `<PREFIX>-deploy`, `<PREFIX>-test`, `<PREFIX>-skill`, `<PREFIX>-docs`. `<PREFIX>-design` is added only when a Frontend category is present. `<PREFIX>-deploy` is the single source of truth for *how* the project deploys — owns `deploy-config.yaml` and the gate/trigger/verify logic; agents, commands, and other skills delegate here. `<PREFIX>-dev` invokes it for non-prod (mid-pipeline, so QA tests a running stack); **prod deploy is invoked only at the command top level** (`/code|/fix --prod`), never from a subagent, because the gate needs `AskUserQuestion` and that only reaches the user at the top level. The deploy skill is **model-invokable** (no `disable-model-invocation` frontmatter) so the dev step and the command can call it via the Skill tool — "never deploy on whim" is enforced by its description + the prod `user_confirm` `AskUserQuestion` gate, not a frontmatter gate.
- **Commands:** thin entry points that hand work to agents — `/code` and `/fix` start the pipeline at `<PREFIX>-dev`; `/tweak` is the sanctioned iterate lane (top-level, inline-verified, batched close-out enforced by the `close-out-gate` hook at push time); `/revert` is the sanctioned rollback (`git revert`, scoped re-verify, logged reversal); others target a specific phase (roadmap, wrap-up, design). `/code` and `/fix` also own the top-level steps the subagents can't do: the Step 0.5 **single gate** (one `AskUserQuestion` call: confirm + verification capture (2–3 candidates + "Other"; a free-text "I'll verify live" is honored as UAT-only, nothing persisted) + regression flag + **Ship** — the ship decision is made up-front while the user is present; `--prod`/`--no-push` pre-answer it; Ship's timeout default is always Hold), the pre-QA "Ensure verification stack" step (start/restart a serve-env with its `stack:` overrides when a UX/E2E target is down or stale — subagents can't hold servers), the user-gated UAT-defer on a `signed-off-with-deferrals` handoff, the subagent salvage protocol (dead agent → SendMessage/re-spawn, never top-level role absorption), and, with `ship_mode: prod`, the post-sign-off prod deploy via `<PREFIX>-deploy` — pre-authorized by the Ship answer only when the run was clean (clean sign-off, no timeout-auto-decisions, shipped set = reviewed set), else re-gated — plus the final close-out (push per `<PREFIX>-deploy` § Push policy + evidence-verified scorecard). **Gate policy:** every command splits `AskUserQuestion` timeouts by risk — reversible gates proceed with defaults labeled `auto-selected on timeout — not user-confirmed`; irreversible gates (prod deploy, CI-coupled push) park; a timeout is never presented as consent. Same `.md` shape across projects (Claude Code only); concrete set evolves over time.
- **Domain skills:** derived from `CATEGORY_MAP` discovery; path ownership is single-sourced in `<CONFIG_DIR>/hooks/governed-paths.conf`.
- **Hooks:** shell scripts wired in `<CONFIG_DIR>/settings.json` that fire on tool events (`PreToolUse` / `PostToolUse` for Edit, Write, Bash, Skill). Two roles only — *gates* that block actions when an invariant is violated (skill not loaded, dirty tree, uncovered path), and *recorders* that mark session state or warn after the fact. Concrete set evolves; the role split does not.
- **Source-of-truth files:** `governed-paths.conf` (path → skill ownership incl. per-skill self-ownership entries + `DEPLOY_PATHS` + `REF_WATCH`), `deploy-config.yaml` on `DEPLOY_OWNER` (unified env schema — every env declares exactly one of `run:` serve-env / `deploy:` ship-env plus `url`; serve-envs may declare `stack:` for a composed, verifiable local stack; `verify:` is a plain env name; typed verifications resolve to the first non-prod env, never prod), `docs/roadmap.md` (open items), `docs/project-log.md` (delivery log).
- **Delivery log entry format** (`docs/project-log.md`, written by `<PREFIX>-log`): `### YYYY-MM-DD HH:MM · <7-char hash> — <title>` (hash = feature commit, never bookkeeping) + 1–3 sentences + `**Tests:**` + `**Skills:**` + optional `**Deployed:**` / `**UAT-deferred:**` / `**Checklist:**`. Any field added here must be added in the `<PREFIX>-log` template, the workflow.md template, and the upgrade-pass checklist together.
